## 📚 ОСНОВНЫЕ ТЕРМИНЫ И ОПРЕДЕЛЕНИЯ

### **Архитектурные компоненты**

**🔹 Буферный кеш (Buffer Cache)**
- *Что:* Область оперативной памяти для кэширования страниц данных
- *Зачем:* Ускорение доступа к данным (чтение из RAM в 1000 раз быстрее диска)
- *Что делали:* Анализировали размер таблиц в кеше, наблюдали грязные буферы

**🔹 WAL (Write-Ahead Log) - Журнал предзаписи**
- *Что:* Циклический журнал на диске, куда записываются все изменения ПЕРЕД основной записью
- *Зачем:* Гарантия сохранности данных при сбоях
- *Что делали:* Измеряли объем WAL, анализировали восстановление после сбоев

**🔹 LSN (Log Sequence Number)**
- *Что:* Уникальный идентификатор записи в WAL (формат: 0/322487F0)
- *Зачем:* Отслеживание позиции в журнале
- *Что делали:* Использовали для измерения объема WAL-записей

### **Процессы PostgreSQL**

**🔹 Checkpointer (Процесс контрольных точек)**
- *Что:* Процесс, выполняющий принудительную запись грязных буферов на диск
- *Зачем:* Создание точек восстановления, ограничение объема WAL
- *Что делали:* Выполняли CHECKPOINT, наблюдали очистку грязных буферов

**🔹 Background Writer (Фоновый писатель)**
- *Что:* Процесс постепенной записи грязных буферов
- *Зачем:* Распределение нагрузки записи на диск
- *Что делали:* Наблюдали за фоновой записью буферов

**🔹 WAL Writer (Писатель WAL)**
- *Что:* Процесс записи WAL-записей на диск
- *Зачем:* Гарантированная запись изменений перед подтверждением операций
- *Что делали:* Идентифицировали в списке процессов

### **Ключевые понятия**

**🔹 Грязные буферы (Dirty Buffers)**
- *Что:* Буферы в кеше с изменениями, не записанными на диск
- *Зачем:* Отслеживание незаписанных изменений
- *Что делали:* Считали до/после контрольной точки, наблюдали обнуление после CHECKPOINT

**🔹 Контрольная точка (Checkpoint)**
- *Что:* Момент принудительной синхронизации всех данных на диск
- *Зачем:* Создание точки восстановления, управление объемом WAL
- *Что делали:* Выполняли вручную, наблюдали в логах при остановке

**🔹 Транзакция**
- *Что:* Атомарная единица работы (все или ничего)
- *Зачем:* Обеспечение целостности данных
- *Что делали:* Создавали зафиксированные и незафиксированные транзакции

**🔹 Восстановление (Recovery)**
- *Что:* Процесс применения WAL после сбоя
- *Зачем:* Приведение данных в согласованное состояние
- *Что делали:* Наблюдали в логах после immediate-остановки

### **Параметры настройки**

**🔹 full_page_writes**
- *Что:* Запись полных страниц в WAL при первом изменении после контрольной точки
- *Зачем:* Защита от частичных записей при сбое питания
- *Что делали:* Сравнивали объем WAL при on/off (разница ~36%)

**🔹 wal_compression**
- *Что:* Сжатие WAL-записей
- *Зачем:* Экономия дискового пространства
- *Что делали:* Изучали эффективность сжатия

## 🛠️ КЛЮЧЕВЫЕ КОМАНДЫ

### **Мониторинг и анализ**
```sql
-- Процессы
ps aux | grep postgres

-- Размеры данных
SELECT pg_relation_size('table_name');
SELECT current_setting('block_size');

-- Буферный кеш
CREATE EXTENSION pg_buffercache;
SELECT * FROM pg_buffercache;

-- WAL-позиции
SELECT pg_current_wal_lsn();
```

### **Управление**
```sql
-- Контрольные точки
CHECKPOINT;

-- Настройки WAL
ALTER SYSTEM SET full_page_writes = off;
SELECT pg_reload_conf();
```

### **Восстановление**
```bash
# Режимы остановки
brew services stop postgresql                    # Fast
pg_ctl stop -m immediate                         # Immediate

# Аварийное завершение
sudo pkill -9 -f postgres
```

1. **PostgreSQL надежен** благодаря тройной системе: кеш → контрольные точки → WAL
2. **WAL - это "черный ящик"** - гарантирует сохранность данных при любых сбоях
3. **Настройки WAL** позволяют балансировать между надежностью и производительностью
