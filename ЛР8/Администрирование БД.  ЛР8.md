## Цель работы  
Освоить методы резервного копирования и восстановления данных в PostgreSQL, включая логическое и физическое копирование, а также углубить навыки управления правами доступа пользователей.
## Теоретическая часть  
- Логическое резервное копирование: Выполняется утилитами pg_dump и pg_dumpall. Создает дампы SQL-команд для восстановления структуры и данных. Гибкое, но может быть медленным для больших БД.
- Физическое резервное копирование: Копирование файлов данных кластера с помощью pg_basebackup. Быстрее, но требует архивации WAL для восстановления на момент времени (PITR).
- WAL-архивация: Непрерывное сохранение сегментов WAL. Позволяет восстанавливать данные на любой момент времени после создания базовой резервной копии. 
- Обновление сервера: Процесс миграции данных на новую мажорную версию PostgreSQL, часто с использованием логического дампа/восстановления.

#### 3. Восстановление кластера  
``` bash
# Создаем временный каталог в домашней директории
mkdir -p ~/postgres_cluster_new
initdb -D ~/postgres_cluster_new -U postgres

# Запускаем на другом порту
pg_ctl -D ~/postgres_cluster_new -o "-p 5433" -l ~/postgres_cluster_new/logfile start
```

``` bash
#!/bin/bash

DUMP_DIR="./all_dbs_dump"
PGHOST=localhost
PGPORT=5433
PGUSER=postgres

echo "Starting cluster restoration..."

# Создаем и восстанавливаем каждую БД
for db_dir in "$DUMP_DIR"/*; do
    if [ -d "$db_dir" ]; then
        db_name=$(basename "$db_dir")
        echo "Restoring database: $db_name"
        
        # Создаем базу данных
        createdb -h $PGHOST -p $PGPORT -U $PGUSER "$db_name"
        
        # Восстанавливаем данные
        pg_restore -h $PGHOST -p $PGPORT -U $PGUSER -d "$db_name" -j 4 --verbose "$db_dir"
        
        echo "Database $db_name restored successfully"
    fi
done

echo "All databases restored to new cluster on port 5433"
```

## Выводы  

#### Основные вопросы и ответы

##### 1. В чем принципиальная разница между логическим и физическим резервным копированием?

**Логическое копирование:**
- Сохраняет структуру БД и данные в виде SQL-команд
- Выполняется утилитами `pg_dump` и `pg_dumpall`
- **Преимущества:** Гибкость (можно восстанавливать отдельные объекты), переносимость между версиями PostgreSQL, сжатие данных
- **Недостатки:** Медленнее для больших БД, требует больше ресурсов при восстановлении

**Физическое копирование:**
- Копирует файлы данных кластера напрямую
- Выполняется утилитой `pg_basebackup`
- **Преимущества:** Высокая скорость для больших БД, минимальная нагрузка на сервер
- **Недостатки:** Требует архивации WAL для PITR, менее гибкое восстановление

##### 2. Какие преимущества дает WAL-архивация и PITR?

**WAL-архивация позволяет:**
- Восстанавливать данные на любой момент времени после создания базовой копии
- Минимизировать потерю данных (до нескольких секунд)
- Обеспечивать непрерывность работы системы

**PITR (Point-in-Time Recovery) обеспечивает:**
- Восстановление до конкретного момента времени (`recovery_target_time`)
- Восстановление до определенной транзакции (`recovery_target_xid`)
- Немедленное восстановление до последней доступной точки (`recovery_target = 'immediate'`)

##### 3. Как управление доступом интегрируется с резервным копированием?

- Привилегии пользователей сохраняются в дампах через `pg_dumpall --globals-only`
- Настройки `pg_hba.conf` критичны для автоматизации бэкапов
- Роли с правами SUPERUSER необходимы для физического копирования
- Правильная настройка прав обеспечивает безопасность резервных копий

##### 4. Какие основные проблемы могут возникнуть при восстановлении?

**При логическом восстановлении:**
- Несовпадение кодировок символов
- Ошибки формата данных в командах COPY
- Отсутствие зависимых объектов (расширений, табличных пространств)
- Конфликты прав доступа

**При физическом восстановлении:**
- Отсутствие или повреждение WAL-файлов в архиве
- Неправильная настройка `restore_command`
- Конфликты табличных пространств
- Несоответствие версий PostgreSQL

##### 5. Сравнительная характеристика методов резервного копирования

| Критерий | Логическое копирование | Физическое копирование |
|----------|------------------------|------------------------|
| **Скорость бэкапа** | Средняя | Высокая |
| **Скорость восстановления** | Низкая | Высокая |
| **Гибкость** | Высокая | Ограниченная |
| **Размер бэкапа** | Компактный (сжатие) | Большой (полное копирование) |
| **Требования к хранилищу** | Умеренные | Высокие |
| **Сложность настройки** | Низкая | Высокая |
| **PITR поддержка** | Нет | Да |

##### 6. Рекомендации по выбору стратегии резервного копирования

**Для небольших БД (до 100 ГБ):**
- Ежедневные логические дампы в формате custom
- Хранение нескольких последних копий
- Простота реализации и восстановления

**Для средних и крупных БД (100 ГБ+):**
- Еженедельные физические базовые копии
- Непрерывная архивация WAL
- Ежедневные логические дампы ключевых объектов

**Критичные системы:**
- Комбинированный подход: физические копии + логические дампы
- Репликация для высокой доступности
- Регулярное тестирование процедур восстановления

##### 7. Ключевые выводы

1. **Резервное копирование должно быть регулярным и автоматизированным**
2. **Тестирование восстановления не менее важно, чем создание бэкапов**
3. **Документация процедур восстановления обязательна для администрирования**
4. **Мониторинг успешности бэкапов критически важен**
5. **Стратегия должна учитывать RPO (допустимую потерю данных) и RTO (время восстановления)**
