## Теоретическая часть
- **Блокировки:** Механизм, обеспечивающий согласованность данных при параллельном доступе. Бывают разных уровней: объекты, строки, буферы в памяти.
- **Мониторинг:** Набор представлений и функций для отслеживания активности сервера, статистики использования объектов и блокировок.
- **Взаимоблокировка (Deadlock):** Ситуация, когда две или более транзакции ожидают друг друга, освобождения ресурсов.

1. **Предикатные блокировки** - PostgreSQL блокирует не только конкретные строки, но и "предикаты" (условия WHERE), чтобы предотвратить фантомное чтение.
2. **Повышение уровня** - Когда конфликт затрагивает много строк или сложные предикаты, PostgreSQL может установить блокировку на уровне таблицы.
3. **Ложные ошибки** - В SERIALIZABLE некоторые безопасные сценарии могут вызывать ошибки сериализации из-за избыточно строгих проверок.
4. **SSI (Serializable Snapshot Isolation)** - Механизм, который отслеживает конфликты между транзакциями и прерывает одну из них.

#### Задача 3: Взаимоблокировка UPDATE

```sql
-- Создание таблицы
CREATE TABLE deadlock_test (id SERIAL PRIMARY KEY, value INT);
INSERT INTO deadlock_test (value) VALUES (1), (2);

-- Сеанс 1
BEGIN;
UPDATE deadlock_test SET value = value + 1 WHERE id = 1;

-- Сеанс 2  
BEGIN;
UPDATE deadlock_test SET value = value + 1 WHERE id = 2;

-- Сеанс 1
UPDATE deadlock_test SET value = value + 1 WHERE id = 2;

-- Сеанс 2
UPDATE deadlock_test SET value = value + 1 WHERE id = 1;
```

**Невозможно** создать взаимоблокировку, если две транзакции выполняют по одному `UPDATE` на **одной и той же таблице**, если они изменяют **одни и те же строки**. Первый `UPDATE` захватит блокировки, второй будет ждать. Это простое ожидание, а не взаимоблокировка.

Взаимоблокировка требует **цикла ожидания**, который может возникнуть, если транзакции обновляют **разные наборы строк** в разном порядке или если задействовано **несколько таблиц**.
